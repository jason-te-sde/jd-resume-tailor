# Verifier evaluation

This directory measures the fact-consistency verifier (`tailor verify`) on labelled examples. It
needs no model: the dataset is fixed text and the verifier is deterministic, so CI runs it on every
push and fails if the holdout numbers get worse.

```sh
uv run tailor eval verifier                  # dev and holdout, writes results.json
uv run tailor eval verifier --split dev      # for tuning: dev only, writes nothing
uv run tailor eval verifier --check          # the CI gate: holdout against results.json
uv run tailor eval verifier --write-split    # after adding rows: new rows go to dev
uv run tailor eval verifier --data eval/verifier/blind --score-only   # the blind set, no split
```

`--score-only` scores every row of a dataset (`labeled.jsonl`, or `rows.jsonl` as in the blind set)
with no split, prints the table, writes nothing, and is not part of the gate.

## What a row is

`entry` is a bank entry of the invented Alex Rivera bank (`examples/alex-rivera/bank.json`), so its
tech stack and its DO NOT CLAIM list apply. `sources` are the exact texts of facts of that entry
(a test and the evaluation itself refuse a source that is not one). `bullet` is a rewrite of them.
`labels` is `["ok"]` or one or more of `fabricated_number`, `number_drift`, `fabricated_entity`,
`do_not_claim`, `escalation_absolute`, `escalation_causal`. A bullet with two problems has two
labels, for example `exactly-once` on the Kafka consumer is `do_not_claim` and `escalation_absolute`.

## How the rows were made

Hand-written, by one person, from the bank. Nothing is generated by a model. Two groups:

- **`pattern-` rows (89)** adapt overclaim patterns found when checking real resume bullets against
  their source repositories, onto Alex's invented projects. Twelve shapes, each written several
  ways: `exactly-once` where the source says at-least-once with an idempotent consumer; "guaranteed
  zero loss" where the source says no loss across N seeded fault-injection runs; 0.875 written as
  88%; a throughput measured at full load next to a latency measured at half load; 29.5 s written
  as 29s beside a flattering comparison; "8K+" where the source says exactly 8,000; "by
  group-committing writers" where the benchmark was single-threaded and the source credits a
  bigger write buffer; "spreading read load" where no load spreading was measured; "up to 3.1x"
  from 3.08x; naming a tool the project never used; "3 custom tools" where one tool did the work;
  a "production model" where nothing was deployed. None of the original names appear.
- **`synth-` rows** are written from the bank facts: faithful rewrites for `ok`, and for each class
  the ordinary ways a rewrite goes wrong (a made-up count, a rounded-up figure, an unrelated
  technology, a claim from the DO NOT CLAIM list, "always", "by <unsupported mechanism>"). 32 of
  them (`synth-reduction-*`, `synth-binding-*`, `synth-scope-*`, `synth-claim-*`) were added to
  **dev** after an independent review of the first version found four shapes the verifier got
  wrong: a percent reduction rounded up ("by 41%" from 40.6%), a number borrowed from another cited
  fact, a number taken from a scope note, and a claim of production or leadership that no fact
  makes. One of them (`synth-binding-05`, a number that is in the cited fact but belongs to another
  claim of the same fact) is known to be missed; it stays in.

The figures of the invented bank were changed once, after that review, by a shift that keeps every
rounding relation (what rounds up and what rounds down, which pairs are one rounding apart). Every
row's verdict was compared before and after, row by row, and none changed: that is how the labels
were kept true without being rewritten.

Several rows were written knowing the verifier cannot catch them (the full-load/half-load pairing,
a "production" claim phrased away from the DO NOT CLAIM wording, "to take read load off"); they
stay in. The point is to measure, not to look good.

Labels say what a careful reader would say about the bullet given its sources and the entry's DO
NOT CLAIM list, not what the verifier says. While tuning on dev I corrected two labels (a causal
claim I had not labelled) and one bullet (it cited a number from a fact it did not list), and
replaced two `ok` rows that were verbatim copies of a bank bullet. No label was changed to match
the verifier.

## The split

The holdout was drawn once, 30% of the rows by `sha256(seed + ":" + id)`, and `split.json` records
which rows are on which side. It does not change: a row added later goes to dev, so no rule can be
tuned on, or tested on, a row that was added after it. (When the rows were renamed from the old id
prefix to `pattern-`, the same 84 rows stayed in the holdout.) The rules were tuned on the dev rows
only (`--split dev` prints dev and writes nothing); the holdout was evaluated once at the end of
each round, and the numbers below are from it.

Read these with the sample sizes in mind: the holdout has 5 to 18 rows per class, so one row is
6 to 20 points of recall, and a class that scores 1.00 on 7 rows says little about the next 70.
The dev numbers (more rows, and the rules were fitted to them) are a more stable estimate, and
they are lower for causal and do-not-claim. The author wrote both the rules and the rows, which
makes every number here optimistic for text the author did not anticipate: on the blind set the
same rules score lower (see the top-level README). The pipeline evaluation
([eval/pipeline/](../pipeline/README.md), a model rewriting the bank's bullets) is the test of that.

The class that is weak is **do_not_claim**: precision 1.00 but recall 0.67 on the holdout and 0.88
on dev. It fires when the bullet repeats the words of a DO NOT CLAIM item, and, since the review,
when a bullet says `production` that no fact says; it still misses a claim made in other words and,
by construction, a number placed in the wrong context within one fact.

## What the verifier cannot see, by design

- **Binding is word overlap.** A bullet number must share a metric word with the fact it matches
  (`verify/binding.py`), which stops `412 ms to 11 minutes` from borrowing another fact's deploy
  time. It cannot tell two numbers of one fact apart (`synth-binding-05`: `31 alerts` where the
  fact says 23 alerts and pages falling from 31), and it flags a number whose metric the bullet
  names in words the fact does not use (`response time` for `latency`).
- **A scope is not evidence of an achievement.** Its numbers are not sources, so a bullet that
  restates a test condition from a scope note (`a median of 5 runs`) is flagged.
- **Context for a true number.** `41,000 checks/s with a p99 of 2.1 ms` has two true numbers that
  were measured at different loads. The checks see numbers and words, not conditions. Only a DO
  NOT CLAIM item that repeats the words catches it.
- **A claim in other words.** "Put it into production" is caught by the `production` rule only
  when no fact says the word; "shipped to customers" is not.
- **Which noun a count belongs to.** Counts are one family: `40 alerts` is read against `31 pages`
  and found to be 31 rounded up (`number_drift`, labelled `fabricated_number`).
- **Derived numbers.** `by 66%` from 412 ms to 138 ms is a number the sources do not contain, so
  it is `fabricated_number`; put derived numbers in the bank as facts.
- **Escalation is heuristic.** It reads English with word lists and stems. "complete coverage" is
  not on the list. "through any outage" is read as a mechanism. A paraphrase that shares too few
  words with its source is flagged (`Found all bugs ... with the simulator`).

## The gate

CI runs `tailor eval verifier --check`, which recomputes the holdout and exits 1 if any metric is
more than 0.02 below `results.json` (or the false-alarm rate more than 0.02 above it). The blind
set is not in the gate. On the 84 holdout rows, 0.02 is less than one row of any class (5 to 18
rows each) and of the 27 ok rows: in practice any change that makes the verifier miss one more
holdout row, or flag one more, fails. That is the intent. Changing the rules to improve the
numbers means rerunning `tailor eval verifier` and committing the new `results.json` with the
reason in the commit message; changing the dataset means `--write-split` as well.
